# Desk MVP Refactorying Strategy

## Objective
Refactor the current solution into a secure desktop-first application with a reliable empty database bootstrap, development-only mock testing tools, and a production runtime that uses only real email providers.

## Core Principles
- Desktop-first: no local web API required for runtime.
- Empty-first boot: first launch must work with a brand-new database.
- Mock-first development: validate workflows internally without real email accounts.
- Production purity: mock/dummy tooling is excluded from release builds and user UX.
- Security-by-default: minimal exposed surface, minimal trusted dependencies.
- Incremental change: preserve working business rules while replacing architecture.

## Target Architecture
- UI layer: native desktop UI (recommended Windows-native stack).
- Application layer: in-process services for contacts, status, messages, sync.
- Data layer: SQLite local DB + schema migrations.
- Integration layer: provider abstraction with RealEmailProvider in production and MockEmailProvider in development builds only.
- Security layer: OS-protected secret storage, strict config and dependency policy.

## Refactoring Phases

### Phase 0 - Baseline and Safety Rails
Goals:
- Freeze behavior of current working features (status + email flow logic).
- Define acceptance tests for startup, status transitions, and message handling.

Actions:
1. Document current business rules and expected status transitions.
2. Add regression tests around those rules.
3. Create dependency allowlist policy and version pinning policy.

Exit Criteria:
- Tests capture expected behavior independent of current transport (HTTP).

### Phase 1 - Empty DB Bootstrap (Highest Priority)
Goals:
- Ensure installer + first run always creates a valid empty DB.
- Remove implicit startup seed assumptions.

Actions:
1. Implement deterministic bootstrap sequence:
   - Resolve app data path.
   - Create DB file if missing.
   - Create schema.
   - Insert only technical metadata (schema_version), no business seed rows.
2. Add startup checks that tolerate zero rows in all business tables.
3. Add command or UI action: Reset Database to Empty.

Exit Criteria:
- Fresh install launches with empty DB and no errors.
- App remains fully usable with zero data.

### Phase 2 - In-Process Service Extraction
Goals:
- Remove dependency on local REST endpoints for app runtime.

Actions:
1. Extract domain services from route/controller patterns.
2. Replace UI HTTP calls with direct service calls.
3. Keep service interfaces stable for testing.

Exit Criteria:
- UI works without backend server process or localhost port.

### Phase 3 - Mock Email Environment
Goals:
- Fully test send/receive/status logic without real accounts.

Actions:
1. Introduce EmailProvider interface:
   - sendMessage(...)
   - fetchNewMessages(...)
   - testConnection(...)
2. Implement MockEmailProvider:
   - Sent messages stored in local outbox table.
   - Synthetic inbound replies generated by rule-based simulator.
3. Add controls:
   - Enable/disable mock mode.
   - Generate test inbox events.
4. Gate all mock tooling behind development build flags and exclude from production artifacts.

Exit Criteria:
- End-to-end email workflows pass using only mock provider.
- Production build contains no mock provider UI/actions.

### Phase 4 - Dummy Data Framework
Goals:
- Support realistic testing on clean installs.

Actions:
1. Build explicit one-click Generate Dummy Data action.
2. Generate contacts, categories, templates, attachment metadata, and message history.
3. Keep generation idempotent options:
   - Additive mode.
   - Replace mode.
4. Restrict dummy-data generation tools to development/QA builds only.

Exit Criteria:
- Team can test all major screens/workflows from empty DB in minutes.
- Production build has no dummy-data entry points.

### Phase 5 - Real Email Provider Integration
Goals:
- Safely connect to user email only after mock-mode maturity.

Actions:
1. Implement RealEmailProvider for SMTP/IMAP and OAuth-capable providers.
2. Enforce TLS and strict cert validation.
3. Store credentials/tokens only in OS-protected storage.
4. Limit sync scope and frequency to least privilege required.

Exit Criteria:
- Real send/receive works with secure storage and no plaintext secrets.

### Phase 6 - Installer and Packaging
Goals:
- Professional installer with deterministic first-run behavior.

Actions:
1. Installer ships binaries and config defaults only.
2. Installer does not ship populated user DB.
3. First-run wizard:
   - Create empty DB.
   - Connect real email account (OAuth Gmail or SMTP/IMAP).
4. Add uninstall behavior policy for user data retention/removal choice.
5. Validate release artifact policy: no mock provider or dummy-data modules included.

Exit Criteria:
- Install -> first launch -> empty app works consistently across machines.

## Security Hardening Checklist
- No local network listeners required for normal operation.
- No wildcard CORS in runtime desktop flow.
- Strict input validation in import/export features.
- Signed builds and hash-verified dependencies.
- SBOM generated per release.
- Secrets never logged.
- Optional local DB encryption decision documented.
- Build gate ensures development-only features are excluded from production.

## Dependency Governance
- Keep dependency count intentionally small.
- Approve libraries through a manual review gate.
- Pin exact versions and lock files.
- Block CI if unapproved dependencies appear.

## Delivery Milestones
1. M1: Empty DB bootstrap stable.
2. M2: UI running on in-process services.
3. M3: Mock email + dummy data complete.
4. M4: Real email provider secure integration.
5. M5: Installer finalized and repeatable.

## Risks and Mitigations
1. Risk: hidden assumptions about seeded rows.
   Mitigation: strict empty-DB test suite and startup assertions.
2. Risk: regressions in status transitions.
   Mitigation: behavior-locking tests before service extraction.
3. Risk: security drift through package creep.
   Mitigation: dependency allowlist + CI enforcement.
4. Risk: provider-specific email edge cases.
   Mitigation: keep provider abstraction and add conformance tests.
